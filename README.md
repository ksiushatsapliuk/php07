# Практична робота 07 — варіант 18

## Мета роботи
Навчитися вимірювати продуктивність власного PHP-застосунку (час виконання, використання пам'яті), проводити просте навантажувальне тестування засобом Apache Bench (ab) і застосовувати базові прийоми оптимізації - кешування результатів запитів, індекси бази даних, зменшення кількості SQL-запитів на один HTTP-запит.

## Запуск
Потрібні PHP 8.1+, MySQL 8.0+, pdo_mysql та mbstring. Увімкнути MySQL і перевірити config.php: за замовчуванням порт 3307, база practicum7.

З кореня php07 один раз виконати встановлення або оновлення старої БД:
```powershell
& C:/php/php.exe -d extension_dir=C:/php/ext -d extension=pdo_mysql tools/install.php
```
Повторний запуск безпечний: наявні рослини зберігаються, додаються лише відсутня обчислювана дата та індекси. sql/schema.sql створює таблицю без вторинних індексів. Окремий sql/indexes.sql містить CREATE INDEX; lib/migrations.php перевіряє метадані перед застосуванням. Для повторення міграції використовувати install.php, а не вдруге імпортувати сирий indexes.sql.

Запуск каталогу:
```powershell
& C:/php/php.exe -d extension_dir=C:/php/ext -d extension=pdo_mysql -d extension=mbstring -S localhost:8000
```
Відкрити http://localhost:8000/index.php. Оформлення, пошук, сортування, CRUD і полив збережено. Публічний API: api.php?resource=plants; GET списку/запису, POST створення та POST action=water. Параметри списку: q, interval=1..3650, due=0/1. Формат: success та data або error; meta містить загальні total і needs_water.

## Структура та обов’язкові контрольні версії
- classes/, lib/, assets/ — код каталогу й ресурси.
- sql/ — схема, окремі CREATE INDEX та міграція дати.
- tools/install.php — встановлення; tools/benchmark.php — відтворення експерименту.
- benchmarks/original06.php — базовий списковий алгоритм API 06 без нового групового підрахунку. Використовує спільні бібліотеки; повної копії старого проєкту немає.
- benchmarks/BeforeGarden.php — збережений N+1: COUNT для кожної рослини в циклі.
- benchmarks/UncachedGarden.php — оптимізований список без кешу для окремого контролю кешування.
- results/ab.txt — вихідний журнал усіх семи AB-серій; results/summary.json — метрики, 70 окремих вимірів, SQL, параметри й плани EXPLAIN.
- docs/ — завдання PDF та звіт Word. README — єдине текстове пояснення.

Три файли benchmarks використовуються засобом перевірки та потрібні для вимог «до/після». Вони не є додатковими сторінками робочого каталогу. Базовий endpoint закритий без спеціального оточення тимчасового Apache.

## Відтворення з репозиторію
Для benchmark додатково потрібні curl у PHP CLI, Apache та ab. З кореня php07:
```powershell
& C:/php/php.exe -d extension_dir=C:/php/ext -d extension=pdo_mysql -d extension=curl tools/benchmark.php
```
За замовчуванням Apache та AB шукаються в C:/xampp/apache/bin, порт 8101. Параметри: --httpd, --ab, --port, --results; --work-dir має бути новою папкою. Без нього створюється унікальна тимчасова папка. Окрема php06 не потрібна.

Сценарій створює власну тестову БД зі своєї sql/schema.sql, фіксує EXPLAIN до індексів, застосовує міграцію двічі й фіксує план після. Тому наявний індекс не спричиняє Duplicate key name. У finally зупиняється власний Apache та видаляється власна БД; робочі дані не змінюються. Новий запуск замінює обидва файли results; старий summary видаляється на початку, щоб невдалий запуск не виглядав завершеним.

## Вісім кроків PDF та виправлення зауважень
1. Базовий список 06 вимірюється через microtime(true), memory_get_peak_usage(true).
2. Для нього виконується AB -n 200 -c 20 -k.
3. MeasuredPDO рахує виконані query/execute; BeforeGarden показує N+1.
4. CREATE INDEX винесено в sql/indexes.sql. EXPLAIN використовує Garden::getListQuery — той самий повний SQL і параметри, що API. interval доступний у формі каталогу. Для таблиці p у тесті interval=7: ALL/500 → ref/5 через idx_plants_watering_interval; полив: ALL/500 → range/20 через idx_plants_next_watering.
5. GROUP BY/JOIN замінює COUNT у циклі: 503 → 3 SQL; JSON збігається.
6. needsWaterToday кешує список на 60 секунд та використовує індексовану next_watering_at <= CURDATE(). Дату автоматично обчислює MySQL. Кеш скидається після CRUD і поливу; перевіряється дата. Контроль без кешу й HIT повертають однаковий JSON.
7. Повторюються профілювання й той самий AB-тест на оптимізованій версії.
8. Нижче наведено таблицю та пояснення; усі вихідні дані збережено у двох файлах results.

Для списку поливу порядок ID збережено сортуванням у PHP, щоб ORDER BY не спонукав MySQL до сканування PRIMARY. FORCE/IGNORE INDEX не використано. Вкладений GROUP BY обробляє каталог; 5 і 20 — оцінки доступу до p, а не всіх частин запиту. На інших даних оптимізатор може обрати інший план.

## Результати одного актуального запуску
Час: 2026-11-03T13:07:28+02:00 — 2026-11-03T13:08:08+02:00. PHP 8.5.10, MySQL 8.0.43, Apache 2.4.58 WinNT, 32 потоки. Дані: 500 рослин; інтервал i%100+1, кожна 25-та прострочена на 1 день, решта полита сьогодні. Поливу потребують 20 записів.

Перед кожною AB-серією виконано 10 профільованих запитів. Усі сім серій завершили по 200 запитів із 20 клієнтами, Failed requests=0, без Non-2xx. Keep-Alive (-k) однаковий для всіх.

| Сценарій | PHP мс | SQL | МБ | Запитів/с | AB mean мс | Помилок |
|---|---:|---:|---:|---:|---:|---:|
| Базовий список 06 | 22.72 | 3 | 2.00 | 175.24 | 114.13 | 0 |
| N+1 без індексів | 447.91 | 503 | 2.00 | 19.16 | 1043.90 | 0 |
| N+1 полив | 29.87 | 23 | 2.00 | 162.38 | 123.17 | 0 |
| N+1 з індексами | 383.14 | 503 | 2.00 | 20.37 | 982.00 | 0 |
| GROUP BY список | 72.15 | 3 | 2.00 | 126.11 | 158.59 | 0 |
| GROUP BY полив без кешу | 14.55 | 3 | 2.00 | 179.89 | 111.18 | 0 |
| Кеш HIT полив | 10.07 | 2 | 2.00 | 177.08 | 112.94 | 0 |

PHP мс — середнє 10 вимірів; МБ — максимальний пік PHP. AB mean — перший Time per request: 20 × тривалість серії / 200 × 1000. Другий рядок — тривалість / 200 × 1000, приблизно 1000/RPS. Це різні показники; жоден не прирівнюється до внутрішнього часу SQL або PHP.

503 SQL = 500 COUNT + SELECT списку + SELECT загальних лічильників + SET time_zone. Для GROUP BY — 3, для HIT — 2; загальні лічильники й налаштування часу залишаються. Перший MISS: 20.13 мс, 3 SQL. Пам’ять у серіях — 2 МБ, її зниження не доведено.

Початкова 06 вже не мала N+1 і не повертала новий same_interval_count. Для оцінки групування порівнювати N+1 з індексами та GROUP BY з тими самими індексами; для кешу — GROUP BY поливу без кешу та HIT. На цій малій вибірці кеш зменшив SQL, але не підвищив RPS. Час залежить від стану комп’ютера; універсальне прискорення не заявляється.
